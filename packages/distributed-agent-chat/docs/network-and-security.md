# Network and secure setup

## Local synthetic development

`npm run doctor` checks only the coordinator: Node.js 22+, `.env` secret validity, and readable `dist/worker.js`. It does not start or validate a worker, executable, Codex shim, or provider. On the worker host, `npm run worker` validates configuration (including Windows executable policy), then starts polling; it does not verify provider credentials or coordinator reachability during startup. Optional `AGENT_DOCTOR=1` checks the configured executable with `--version` and makes no provider call, but is not a worker health probe. To establish worker health, run `npm run worker` with the complete exported environment on that host and verify a synthetic MOCK turn end-to-end.

Use Node.js 22+, `npm ci`, `npm run build`, `npm test`, then `npm run dev -- --ip 127.0.0.1`. The dev server is for local development, not an internet-facing deployment. Configure secrets through Wrangler's local secret mechanism and keep secret files out of version control. Use separate random values for chat and each worker token. Do not pass tokens as URL parameters or command-line arguments.

Start agent workers only after configuring an explicit target (`AGENT_ID` is any valid target ID), stable worker identity, trusted `AGENT_CWD`, `AGENT_MODE` (`pi`, `claude`, `codex`, `opencode`, or `mock`), and the matching token. Target ID and runtime mode are independent; absent `AGENT_BINARY`, the mode selects the executable. On Windows, `AGENT_BINARY` must be an absolute native `.exe` (not `.cmd` or `.ps1`; mock is exempt). Set `AGENT_MODEL` and (where supported) `AGENT_PROVIDER` explicitly; adapter mappings differ: Pi passes provider/model flags; Codex uses Ollama-specific local-provider arguments for Ollama and generic provider configuration otherwise; OpenCode uses a provider/model namespace; Claude accepts no generic provider or exactly case-sensitive `ollama` with `ANTHROPIC_BASE_URL`; mock ignores provider/model. Pi, Codex, and OpenCode do not get an Ollama-specific endpoint or credential injected. Examples: Pi: `AGENT_MODE=pi AGENT_PROVIDER=ollama AGENT_MODEL=qwen-coder`; Codex: `AGENT_MODE=codex AGENT_PROVIDER=ollama AGENT_MODEL=qwen-coder`; OpenCode: `AGENT_MODE=opencode AGENT_PROVIDER=ollama AGENT_MODEL=qwen-coder`; Claude: `AGENT_MODE=claude AGENT_PROVIDER=ollama AGENT_MODEL=...` with `ANTHROPIC_BASE_URL` and compatible Anthropic environment. These are illustrative configuration examples, not executed; the worker never launches/installs Ollama or pulls a model, and no live provider behavior is verified. Pi native extensions, skills, and prompt templates remain disabled by default; only opt in with `AGENT_PI_TRUSTED_NATIVE=1` for trusted local installations. Headless Pi extension UI requests are cancelled (fail-closed), never approved automatically. An agent process can run tools with the permissions of its OS account. Use an unprivileged account and a disposable, narrow workspace; this application is not a tenant isolation boundary or sandbox. Provider credentials and session files remain on their worker host.

## Remote workers

Preferred paths, from simplest to more involved:

1. **HTTPS reverse proxy** in front of the coordinator, with valid TLS, access restrictions, and request body/time limits appropriate to your deployment. Terminate TLS only at a trusted proxy. Keep the coordinator's origin private behind it.
2. **SSH local forwarding** from the worker to a loopback-bound coordinator, e.g. `ssh -N -L 18879:127.0.0.1:18877 user@coordinator-host`, then set the worker's chat URL to `http://127.0.0.1:18879`. Restrict SSH keys and host access.
3. **Private overlay network** with authenticated members and narrowly scoped firewall rules, plus TLS where traffic crosses an untrusted network.

Do not expose a plain-HTTP listener or object-store/internal coordination port publicly. A Bearer token does not encrypt traffic. Do not place credentials in URLs, shell history, logs, issue reports, or screenshots. Rotate a token immediately if exposed. Minimize who can read deployment configuration, environment files, provider homes, and session data. On Unix, set secret files to owner-only permissions; on Windows, use an account-specific directory and restrictive NTFS ACLs (the Unix `chmod` guidance does not apply).

## Standalone and distributed limits

Each room/target session is pinned to its first worker ID and mode; preserve both on restart. Use a new room when switching a target from mock to real mode or changing worker identity; there is no session-reset UI. At most one turn per target per room may be queued or running. History returns the latest 100 runs; prompts are limited to 12,000 JavaScript string code units and accumulated output to 1,000,000. Real adapter runs default to a ten-minute deadline. Target maps support 1–64 IDs, each matching `[A-Za-z0-9_-]{1,64}`.

## Checks

Before connecting remote agents, verify the coordinator is reachable only through the intended path, TLS certificate validation succeeds, tokens are distinct and scoped to their intended worker, and logs do not contain secrets or raw provider stderr/tool arguments. Use synthetic tests; do not authorize provider usage simply to validate transport.
