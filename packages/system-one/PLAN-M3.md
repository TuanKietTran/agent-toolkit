Why: the owner's real history has 0 mid-session model switches and only 24 "new session" picks, so supervised learning of model pick is impossible. We instead (1) write the policy explicitly, (2) distill it into a tiny fast local student, (3) prove it with invariants, (4) log real picks from now on so future data can retrain it.
Be honest everywhere: this distills a policy seeded by the owner's habits; it does not learn the owner's behaviour. Say so in README and STATUS.

HARD RULE still applies: the only decision kind is `model_pick`, every public entry point goes through `DecisionGuard`, no permission-style kinds, no auto-answering prompts. No prompt text anywhere (metadata/hints only).

## M3a: explicit policy (`src/system_one/policy.py`)
Pure function `pick_model(scenario) -> Decision(model, rule, reason)`.
Scenario inputs (no text): `situation` (new|existing|continuing), `prev_model` (None for new), `idle_gap_minutes`, `complexity_hint` (low|medium|high, supplied by the caller; used for new and forced switches), `context_tokens`, `needs_images`, `available` (set of models), `headroom` per provider pool (`claude`, `codex`; 0..1 remaining), `hard_cap` (read the default from `usage-roundrobin.ts`).
Models: claude-cli `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5`; openai-codex `gpt-6-luna`, `gpt-5.6-luna`, `gpt-6-sol`, `gpt-6.1-sol`, `gpt-5.6-sol`, `gpt-5.5`, `gpt-6-astra`. Context windows: claude 200K, codex 272K; take prices from `models-store.json` (cost fields only).
Tiers: low = haiku-5-5, gpt-6-luna, gpt-5.6-luna; medium = sonnet-5-5, gpt-6-sol, gpt-6.1-sol; high = opus-5, gpt-5.6-sol, gpt-5.5, gpt-6-astra.
Rules (evidence: the owner never switches mid-session and resumes on the same model; starts are opus 4, sonnet-5-5 13, haiku 6, i.e. tier follows task size; usage-roundrobin holds a model to keep the prompt cache):
- R1 continuing: hold `prev_model` if it is available, supports the needed input (images), fits context (<= 80% of its window) and its pool headroom is above the cap margin; otherwise forced switch via R3.
- R2 existing: same as R1 (the owner always resumes on the same model); a cold cache alone is not a reason to switch.
- R3 new or forced: pick from the tier of `complexity_hint`; among usable models prefer the provider with more headroom, ties go to the cheaper; forced switches never move below the tier of the model being left unless it is unusable.
Every Decision carries the rule id and a short reason.

## M3b: scenarios and student
- `scenarios.py`: generate synthetic scenarios, **balanced across situations** (e.g. 1/3 each), including edge cases (exhausted quota, image needed, unavailable models, huge context). Deterministic seed. Split train/validation/test 70/15/15 by random scenario, plus an out-of-distribution test set (held-out headroom ranges and a held-out model unavailable) to check generalisation.
- `student.py`: train a small model (`scikit-learn` decision tree or small gradient boosting; ask me before adding anything over ~500 MB). Export the trained model to **JSON** and run inference with pure Python from that JSON (no pickle loading at runtime). Wrap with a **validator** that rejects any pick that is unavailable, lacks image support or overflows context, and falls back to the explicit policy (and counts fallbacks). System 1 proposes, validators dispose.
